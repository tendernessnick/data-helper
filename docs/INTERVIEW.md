## 一、30 秒项目介绍（电梯稿）

> 这是一个我独立开发的**本地数据分析工作台**，FastAPI + pandas/DuckDB 后端、Vue3 + ECharts 无构建前端，自研约一万行、152 项测试。它覆盖数据分析全流程：导入清洗 → 统计/时序/业务模板（RFM、漏斗、同期群留存、A/B、手写 K-means）→ AI Agent 辅助分析。特色是三点：一是**数据不出本机**——AI 只拿列摘要、分析全在本地执行；二是**百万行真实数据实战**——我用它对 UCI 电商百万行交易做了端到端分析并输出了业务结论；三是工程化完整——Parquet 列存、大文件流式导入、SSE 流式、function calling 工具循环、CI/CD、可一键打包 exe 分发。

## 二、STAR 主故事（被问"讲讲这个项目"时）

- **S（背景）**：业务同学手里的 CSV 分析需求重复度高：导入 → 体检 → 清洗 → 出几个图 → 写结论。通用工具（Excel）做不了 RFM/留存这类模板，云端 BI 又涉及数据出境与账号成本。
- **T（目标）**：做一个**零部署、数据不出本机**的分析工作台，把高频分析路径产品化，并能处理百万行级真实数据。
- **A（行动）**：FastAPI + pandas/DuckDB 自研 25 个后端模块；Vue3 无构建前端（本地 vendor，双击 exe 即用）；存储从 pickle 重构为 **Parquet 列存 + 原子写 + 旧数据自动迁移**；大 CSV 分块流式导入；AI 侧从"问答"升级为 **function calling 工具循环**（LLM 出意图、本地真实执行、结果卡回填）；最后用 106 万行 UCI 电商真实数据做端到端验证，沉淀完整分析叙事。
- **R（结果）**：152 项测试全绿、CI 双 Python 版本、ruff 零告警；92MB CSV 上传 2.6 秒；案例产出可复现的量化业务结论（41% 客户贡献 82% 收入等）；exe 一键分发。

## 三、功能深挖话术（面试官往深了问时的弹药库）

### 3.1 存储为什么从 pickle 换成 Parquet？（storage.py）

- **痛点**：pickle 是行存 + Python 专用序列化，体积大、加载慢、还有安全面（反序列化执行）；跨语言不可读。
- **方案**：`current.parquet`（snappy 压缩列存）+ `.tmp` 临时文件 `os.replace` **原子写**（写一半崩溃不留损坏文件）。
- **兼容**：存量数据集首次加载时 `_migrate_legacy()` 自动把 `current.pkl` 转 Parquet 并清理旧快照——**用户无感升级**。
- **深挖点**：病态 object 列（一列里混 str 和 float）pyarrow 序列化会炸，`_write_parquet` 先直写、失败再对 object 列字符串化重试——正确性兜底。
- **追问"为什么不用 SQLite/DuckDB 文件"**：Parquet 是分析型列存，与 DuckDB 视图天然配合；事务能力对本场景（单用户单写者）不必要。

### 3.2 大文件怎么不爆内存？（storage.create_dataset_stream）

- 上传先 8MB 分块落盘临时文件（同时卡 500MB 上限）；>16MB 的 CSV 走**流式建集**：嗅探编码（utf-8-sig/gbk/latin-1）与分隔符（表头计数）后，`pd.read_csv(chunksize=20万)` 逐块读，第一块定 schema，`ParquetWriter` 逐块追加——**内存只驻留一个块**。
- 两个坑的真实处理：① 跨块类型漂移（前 20 万行 int、后面冒出字符串）→ 逐列 `astype` 安全提升，提升失败**整体回退全量解析**（正确性优先）；② 分隔符嗅探误判 → 首块列数校验，不对就回退。回退路径与正常路径产出完全一致的 meta。
- **实测**：92MB / 1,067,371 行电商 CSV，上传 + 建集 2.6 秒。

### 3.3 SQL 是怎么做的？安全性呢？（sqlquery.py）

- 每个数据集注册为 DuckDB 视图：`CREATE VIEW ds1 AS SELECT * FROM read_parquet(?)`——**惰性读取**，查询时聚合下推到列存，不把所有数据集整表载入 Python 内存。
- 只读防护两级判定：语句必须 SELECT/WITH 开头 + 分号拼接的每一段都校验（拦 `SELECT 1; DROP TABLE x`）。**不做全文关键字扫描**——避免误伤列名/字符串里恰好含 update 的合法查询（这是踩过坑的：敏感词表会误伤 `updated_at` 列）。
- 预览 10 万行截断只作用于响应 rows；**另存为数据集不截断**（这里修过一个真 bug：早期把 df 本身截断了，用户建出来的数据集悄悄丢行——有回归测试）。
- DuckDB 细节：CREATE VIEW 不支持 prepared parameter，路径是程序自身生成的，做单引号转义后内联。

### 3.4 手写 K-means，为什么不用 sklearn？（biz.py）

- 三个理由：**零依赖**（exe 体积、安装成功率）、**面试可讲实现细节**、需要与业务模板深度耦合（自动选 k + 簇画像表 + 散点着色）。
- 实现：`k-means++` 初始化（按距离平方概率采样，让初始中心彼此远离）× `n_init` 多重启取 SSE 最小 → 解决局部最优；k 的选择用**肘部法 SSE + 轮廓系数双指标**，轮廓系数 >0.2 才推荐，否则提示结构弱；特征 Z-score 标准化（ monetary 量纲远大于 frequency，不标准化聚类就变成"只按金额分"）；轮廓系数计算对大样本做了 1000 点抽样。
- **实战发现**：电商案例中自动选 k=2（轮廓 0.923）——因为数据里真有"批发/零售"两个物种，最大单客 LTV 是中位数的 677 倍；强制 k=4 得到鲸鱼/高频批发/稳定大众/流失四个可运营簇。这个"自动指标给结构信号、业务需要再细分"的对话我很愿意展开讲。
- 聚类在 **RFM 三指标**上跑，与 RFM 规则分层交叉验证：两种独立方法指向同一批流失人群，结论可信度互相背书。

### 3.5 两比例 z 检验 & A/B 套件（stats_tests.py）

- 场景：A/B 实验的转化率显著性。数据集模式（分组列 + 转化列 + 转化取值）与直接计数模式双输入。
- 输出不止 p 值：**差值的 95% CI + 相对提升**——面试高频点："p<0.05 说明有差异，CI 告诉你差异有多大，业务决策看的是后者"。
- 连续指标补了 **Cohen's d** 效应量及解读（<0.2 可忽略 / 0.2-0.5 小 / 0.5-0.8 中 / >0.8 大），并且 UI 显示 verdict 而不是把"效应量小"误标成"不显著"——**统计显著 ≠ 实际显著**是我想在产品里传递的概念。
- **样本量计算器**：α/power/基线转化率/MDE → 每组 n（正态近似公式），解决"实验要跑多久"的前置问题。

### 3.6 漏斗与同期群留存的口径（biz.py）

- 漏斗用**到达制**口径：用户到达第 i 步 = 完成了 1..i 全部步骤的事件（不校验先后顺序）。为什么？订单/行为日志普遍乱序、时间戳缺失，严格有序漏斗会系统性低估；到达制是业务漏斗最常用宽松口径，note 里明确告知用户。每步输出单步转化、整体转化、较上步流失。
- 同期群留存：按用户首次活跃月/周分群，输出 N 期留存率矩阵 + 群规模，前端 ECharts 热力图（0-100% 蓝色渐变）。实现核心是 `dt.to_period` 打期标签后双 groupby，全部向量化。

### 3.7 AI Agent：function calling 工具循环 + SSE（agent.py）

- **架构原则：LLM 出意图、本地算数据、数据不出本机**。12 个工具（describe/groupby/trend/corr/histogram/value_counts/rfm/funnel/cohort/cluster/prop_z_test/forecast）以 JSON Schema 注册；LLM 发 tool_calls → 后端在当前 DataFrame 真实执行 → 统计结果（截断到 3500 字符）回填 → LLM 解读 → 结果卡直接回填数据页画布。
- **SSE 流式**：OpenAI 兼容接口 `stream=True`，增量 content 包成 `delta` 事件下发；tool_call 增量按 index 累积（name 去重拼接、arguments 分片拼接、缺失 id 本地生成）；工具执行时下发 `tool_start`（前端显示"⏳ 正在执行 RFM 客户分层…"），完成后 `tool_result` 带完整卡片描述。前端 fetch + ReadableStream 手动解 SSE 帧，支持**停止按钮**（AbortController）。
- **健壮性**：端点不支持 tools（400/404 且报文含 tool/function）→ 自动降级纯文本流式并提示；工具参数是 LLM 给的，**可能错**——执行失败把错误信息作为 tool 消息回填，LLM 会自行修正参数重试（有 mock 测试覆盖这条路径）；最多 6 轮防失控，轮次耗尽强制无工具总结。
- **会话历史**：内存级 dict + 锁 + 24 条上限，跨请求上下文连续；重启即清（隐私优先的取舍）。
- 测试策略：mock `_post_llm` 返回脚本化 SSE chunk——工具往返、错误回填重试、降级、历史回放、SSE 协议格式全部可测，不需要真实 key。

### 3.8 时序预测（forecast.py）

- 三方法：线性趋势 / Holt 双参数指数平滑 / 季节性朴素，**留出法回测**（20% 尾部 holdout）按 MAPE 自动选优；网格搜索平滑参数；输出 95% 置信区间带状图。手写 ADF 检验配合金融模块。

### 3.9 前端为什么"无构建"？

- 双击 exe 即用是核心体验，无构建 = 无 node_modules、无 webpack 配置腐烂、版本升级就是换 vendor 文件。Vue3 全局构建 + 单文件 app.js（约 1600 行）+ ECharts 本地 vendor（离线可用）。代价是没了组件化与 HMR——单页规模可控，且静态资源用版本号 query 做 cache-bust。

### 3.10 工程化细节（爱问"项目有什么坑"时用）

- **requirements 曾是坏的**（首行自引用 + 缺核心依赖）→ 重建并在干净 venv 实测安装 + 全量测试。
- **git 历史里混进了 AI 会话目录** → filter-repo 从全部历史剔除（无远程仓库，重写安全），.gitignore 补齐 dist/build/logs 等。
- **api_key 安全**：明文不回传，GET 返回掩码；保存时识别掩码值不覆盖真 key，清空即断开。
- 日志基建：控制台 + `data/logs/app.log` RotatingFileHandler，关键路径（上传/AI 调用/SQL/异常）落日志，静默吞错全部替换。
- 上传 200MB→500MB 放宽（配合流式）；测试沙箱数据目录用环境变量注入，Windows 下 RotatingFileHandler 句柄要在 sessionfinish 里 shutdown 才能清目录——这种平台坑我都遇到过并写进了 conftest。

## 四、高频 Q&A

**Q: 为什么全部本地化？数据不出本机怎么落地？**
A: 目标用户是拿敏感业务数据（客户/订单）的业务同学，云端 BI 有合规与信任成本。落地：存储全在 `data/` 本地目录；AI 是唯一可能外发的路径，只发送**列结构摘要**（列名/类型/缺失率/min/max/高频值），且 key 不配置则 AI 完全关闭。这个边界我会在界面和文档里明确标注。

**Q: AI 辅助写代码，你怎么坦诚信任这个项目的代码能力？**
A: 坦然说开发过程深度用了 AI 结对，但有三道防线：152 项 pytest（含真 bug 回归：SQL 建集截断、undo 快照泄漏、pickle 迁移）保证行为正确；ruff + CI 双版本保证风格与兼容；架构分层清晰（api/agent/analysis/storage 各司其职），人负责设计与验收，AI 负责加速实现。我认为"会用 AI 高质量交付"本身就是这项工程的能力。

**Q: 和 Power BI / Tableau / 六个标准差工具比，差异化在哪？**
A: 三点：本地免部署零信任成本；业务模板原生内置（RFM/漏斗/留存/聚类一键出卡，不需要写 SQL 或 DAX）；AI Agent 是"会动手的"——不是给建议而是直接在数据上执行并回填结果卡。

**Q: 规模上限？**
A: 百万行主战场（案例实测 106 万行全流程秒级）；千万行级取决于列宽与内存，Parquet 列存 + DuckDB 下推已经是同内存预算下的合理上限，再往上该换真正的 OLAP 引擎（ClickHouse），那是另一个产品了。

**Q: 最难的技术问题是什么？**
A: 流式建集的类型漂移问题：pandas 分块读取每块独立推断 dtype，第 2 块一个脏值就让 Arrow schema 冲突。第一版直接失败，第二版逐列安全提升 + 整体回退全量解析，并用 26 行的脏数据测试钉住这个行为。它小，但代表了"流式处理的正确性兜底"这个普适问题。

**Q: 如果重做一次，会改什么？**
A: ① 前端会上 Vite（卡片数量多了之后单文件 app.js 的可维护性确实在下降）；② 会话历史换 SQLite 存储（现在重启丢失）；③ 工具循环加并发工具执行与流式表格增量渲染。

## 六、可现场演示的 60 秒脚本

1. 打开 exe → 点「生成示例数据」→ 一键洞察（质量评分环形图）；
2. 左侧选电商「有效销售明细」→ 业务模板 → RFM → 环形图 + 8 层表（82.08% 一句话）；
3. 切「客户RFM指标」→ K-means k=4 → 散点 + 四簇画像（讲鲸鱼/流失两簇）；
4. 切「客户生命周期事件」→ 转化漏斗 24.8%；
5. 顶部 🤖 → 输入"帮我做同期群留存并解读" → 看工具进度 + 流式解读 + 结果卡自动出现在数据页；
6. SQL 控制台一句 `SELECT Country, SUM(Amount) FROM df GROUP BY 1 ORDER BY 2 DESC LIMIT 5`。
